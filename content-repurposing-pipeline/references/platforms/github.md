# GitHub Platform Profile

Platform ID: `github`

## Position

- Purpose: repository documentation that enables evaluation, installation, use, contribution, and maintenance.
- Reader intent: decide whether the project fits, get a verified first result, or solve a repository-specific problem.
- Best fit: README files, project documentation, release notes, examples, and implementation guides tied to real source code.

## Write

- Title: use the actual project or document name and a literal one-line description.
- Opening: state what exists, its current status, who it is for, and the problem it solves.
- Structure: overview, verified capabilities, prerequisites, install, quick start, usage, configuration, examples, troubleshooting, security, and contribution or license information as applicable.
- Voice: direct, task-oriented, and consistent with repository terminology.
- Depth: derive commands, options, paths, and supported environments from the current source or runnable build.
- Links: use stable repository-relative links where possible and direct readers to issues or discussions only when those channels exist.
- Ending: provide the next concrete repository action, not a marketing CTA.

## Visuals

- Show the actual product, command output, API result, or workflow; keep screenshots close to the feature they prove.
- Use diagrams only when they clarify architecture or contribution boundaries.

## Avoid

- Invented installation steps, unsupported platform badges, stale screenshots, unverified feature lists, copied secrets, and claims that source code cannot support.
- Writing a launch article where maintainable repository documentation is required.

## Platform QA

- Test or inspect the quick start against the current repository and verify every referenced path, command, option, link, and license statement.
- Record a blocker when source, a runnable build, or required credentials are unavailable.
